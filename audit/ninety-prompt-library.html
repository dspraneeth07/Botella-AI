How to use this

  1. Paste the primer first, once per fresh Claude Code session. It establishes the repository's non-negotiable constraints so no later prompt has to repeat them.
  2. One prompt per session. They are sized to be a single coherent change with its own tests. Two at once produces a diff nobody can review.
  3. Do not skip the gate. Each prompt ends in a number that must move. If it does not move, the prompt failed — and that is a finding to publish, not a step to work around.
  4. Run the guards every time: python -m pytest tests/ -q, check_no_literals.py, check_no_state_branches.py.
  5. The tick boxes are remembered in your own browser only. They are a convenience, not shared state — nobody else sees them.
The one instruction that overrides everything else

Never reach 90% by raising the p_hit floor. The engine's own settings already price that path: 0.50 gives 75.9% at 5.1 cards a run; 0.55 buys about one point, cuts coverage to 2.4 cards and halves the margin. A floor high enough to print 90% issues almost nothing.

And never change deficit_units. The +16.6 point edge over a reversion-matched null was measured on that ordering. Moving it invalidates the result and the whole five-store audit has to be re-run.

N8.4

Grade a playbook as one bet, and pool to get any power

GATE — pooled across stores: playbook promise kept ≥85% and net margin per playbook significantly positive.
TASK: measure the playbooks honestly, which means admitting how little power one
store-year has.

THE POWER PROBLEM, STATED FIRST
A playbook fires ONCE A YEAR. One store-year is n = 1. A playbook can never be
significant on its own, and printing a per-store verdict on n = 1 would repeat
the row-wise-bootstrap mistake that was already caught here and thrown away - it
reported "82.9%" off 41 observations.

WHAT TO BUILD
- Grade the playbook AS A UNIT: did realised units over the event window clear
  the promised total, and what was the net margin after N0.1's holding cost.
  Not line by line - the owner made one decision.
- POOL ACROSS STORES AND ACROSS EVENTS for any verdict. State the pooling
  explicitly in the report. This is the one family whose evidence is necessarily
  cross-sectional, and hiding that would be dishonest.
- The backtest is available TODAY, before any live playbook ships: 3.7 years of
  history contains three or four occurrences of every event, so a walk-forward
  over past events can be run immediately. Do that first and report it.

GUARDRAILS
- No per-store verdict on one occurrence. An interval, yes. A verdict, no.
- Date-clustered: all lines in one playbook share one event, so they are one
  cluster, not thirty observations.
- The LEAD TIME benefit - an owner told six weeks ahead can negotiate,
  consolidate a delivery and use supplier terms - is real and is NOT incremental
  margin on units. If it is claimed anywhere, it must be measured separately.
  This prompt does not pretend to measure it, and the report must not imply it.

TESTS
    test_playbook_graded_as_one_unit
    test_no_per_store_verdict_on_one_occurrence
    test_playbook_lines_are_one_cluster

THEN: run the historical walk-forward over all past occurrences of all events at
all five stores and give me the pooled result. If playbooks do not clear the
gate, switch the family off and add a row to ENGINE-ENHANCEMENTS.md section 11
like every other idea that lost.
